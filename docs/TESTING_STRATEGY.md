# FinSignal — Testing Strategy

**Project:** FinSignal — Financial Transaction Intelligence & Investigation Platform  
**Document:** Testing Strategy  
**Status:** Planning / Implementation-Ready  
**Version:** 1.0.0  
**Last Updated:** 2026-10-25

---

## 1. Purpose

This document defines the testing strategy for FinSignal.

FinSignal combines financial data ingestion, deterministic analytics, behavioral feature engineering, machine-learning anomaly detection, investigation workflows, and AI-assisted investigation summaries. Testing must therefore validate not only conventional application behavior, but also:

- financial correctness;
- temporal correctness;
- data lineage;
- prevention of data leakage;
- ML reproducibility and evaluation quality;
- authorization boundaries;
- investigation state transitions;
- evidence integrity;
- AI safety and grounding;
- API contracts;
- database behavior;
- frontend integration boundaries.

The objective is not to maximize a single code-coverage percentage. The objective is to provide evidence that the system behaves correctly, securely, reproducibly, and predictably across its most important failure modes.

---

## 2. Testing Goals

The testing strategy has the following goals:

1. Verify that valid transactions are processed correctly.
2. Prevent invalid, malformed, duplicated, or ambiguous financial data from silently entering the system.
3. Verify that historical features use only information available at the evaluation point.
4. Prevent fraud labels, future transactions, or other target information from leaking into model features.
5. Verify deterministic analytics and financial calculations.
6. Verify ML model reproducibility and evaluation behavior.
7. Verify that suspicious activity produces explainable risk factors rather than unexplained scores.
8. Verify investigation workflows and authorization boundaries.
9. Verify that AI summaries are grounded only in supplied evidence.
10. Verify API contracts and persistence behavior.
11. Detect regressions early through automated CI testing.
12. Keep the test suite fast enough for normal development while reserving slower tests for appropriate CI stages.

# 3. Testing Principles

## 3.1 Test behavior, not implementation details

Tests should primarily verify observable behavior and domain invariants.

Avoid tests that become brittle because of:

- private method names;
- internal helper structure;
- ORM implementation details;
- exact SQL generated by the ORM unless SQL behavior itself matters.

Prefer tests such as:

- a transfer changes balances correctly;
- a transaction cannot be accessed by an unauthorized user;
- a historical feature does not include future transactions;
- an investigation cannot move directly from `OPEN` to `RESOLVED` without required information.

---

## 3.2 Financial correctness has priority

Financial calculations must be tested more strictly than ordinary UI formatting or convenience functionality.

Tests should verify:

- decimal precision;
- currency handling;
- sign/direction semantics;
- aggregation correctness;
- boundary values;
- zero values;
- negative values where applicable;
- large values;
- timestamp boundaries;
- transfer semantics.

Floating-point arithmetic must not be used where exact monetary representation is required.

---

## 3.3 Historical correctness is a first-class requirement

Any feature based on transaction history must be tested against the exact information available at the evaluation timestamp.

For a transaction at time `T`, a feature must not use:

- transactions after `T`;
- future account activity;
- future merchant activity;
- future device/location observations;
- fraud labels;
- investigation outcomes;
- future-derived aggregates.

This requirement applies to both training and inference.

---

## 3.4 Synthetic data must remain reproducible

The synthetic dataset is a core testing asset.

Tests that depend on generated data should use:

- explicit random seeds;
- fixed dataset versions where appropriate;
- deterministic generators;
- controlled scenario injection.

A failing test should be reproducible without depending on the current wall-clock time or uncontrolled randomness.

---

## 3.5 Tests should fail for meaningful reasons

Avoid tests that pass merely because:

- a mocked method was called;
- a response contains a field;
- a status code is returned without validating the body;
- a model object exists;
- a query returns any rows.

Assertions should validate meaningful domain outcomes.

# 4. Testing Pyramid

FinSignal follows a layered testing pyramid.

```text
                    /\
                   /  \
                  / E2E \
                 /------\
                / API /  \
               /Integration\
              /------------\
             / Unit / Domain \
            /---------------\
```

Approximate distribution:

| Test Layer | Primary Purpose | Relative Volume |
|---|---|---:|
| Unit | Domain logic and pure transformations | High |
| Integration | Database, repositories, ML/data pipelines | Medium-high |
| API | HTTP contracts and authorization | Medium |
| End-to-End | Critical user journeys | Low |
| Performance | Capacity and regression checks | Low / scheduled |

The exact number of tests is not prescribed. Test volume should follow risk and complexity.

# 6. Unit Testing Strategy

Unit tests should cover deterministic domain logic without requiring a running PostgreSQL instance or external services.

Primary framework:

- `pytest`
- `pytest-asyncio` where asynchronous application code requires it.

## 6.1 Unit-test targets

Unit tests should cover:

- validation functions;
- normalization functions;
- transaction classification;
- monetary calculations;
- time-window calculations;
- behavioral feature calculations;
- risk-factor generation;
- risk-level classification;
- investigation state transitions;
- evidence construction;
- API validation helpers;
- configuration validation;
- pure ML preprocessing functions;
- model scoring adapters.

---

## 6.2 Financial calculation tests

Examples:

- debit increases spending and decreases available balance where applicable;
- credit is treated as inflow;
- zero-amount transactions are rejected or handled according to the domain rule;
- decimal values retain expected precision;
- aggregation of `0.10 + 0.20` does not introduce binary floating-point errors;
- transactions in different currencies are not silently combined without conversion rules;
- transaction direction is not inferred incorrectly from amount sign.

Boundary tests should include:

- smallest supported amount;
- maximum supported amount;
- exact zero;
- very large amounts;
- decimal precision boundaries.

---

## 6.3 Time-window tests

Test exact boundaries for:

- last 5 minutes;
- last hour;
- last 24 hours;
- daily aggregates;
- monthly aggregates;
- weekend detection;
- unusual-hour detection.

A transaction exactly on the boundary must have a defined inclusion rule.

Example:

```text
window = [T - 1 hour, T]
```

must behave consistently throughout the application.

Timezone behavior must also be tested explicitly.

# 7. Integration Testing

Integration tests verify interactions between application components and real infrastructure.

Primary integration target:

- PostgreSQL.

Integration tests should verify:

- repository queries;
- foreign-key relationships;
- constraints;
- indexes where behavior matters;
- transaction boundaries;
- migrations;
- persistence of risk analyses;
- investigation relationships;
- evidence relationships;
- audit records.

Mocks should not replace PostgreSQL when the behavior under test depends on actual database semantics.

# 8. PostgreSQL Testing

The preferred integration environment is an isolated PostgreSQL instance, typically created through Docker for local and CI execution.

Tests should start from a controlled database state.

## 8.1 Database test requirements

Verify:

- migrations execute successfully from an empty database;
- migrations are repeatable only where explicitly designed to be;
- all required foreign keys exist;
- invalid references are rejected;
- uniqueness constraints work;
- check constraints work;
- indexes support important query paths;
- cascade/restrict behavior matches the data model;
- transaction rollback works.

---

## 8.2 Persistence tests

For every important aggregate, test:

1. creation;
2. retrieval;
3. update where allowed;
4. invalid update;
5. relationship loading;
6. deletion behavior where deletion is allowed.

Immutable financial records must not be casually mutable through generic update paths.

---

# 9. Migration Testing

Every database migration must be tested in CI.

Required checks:

- clean database → all migrations succeed;
- schema matches expected current version;
- representative seed/test data can be inserted;
- important constraints remain valid after migration;
- migration ordering is correct.

Where practical, test migration upgrades from the previous supported schema version.

Destructive migrations require explicit review.

Roles:

- `ADMIN`
- `ANALYST`

- each role can access permitted endpoints;
- each role is denied restricted operations;
- users cannot access another user's protected resources without authorization;
- object ownership or permitted investigation scope is enforced;
- changing URL identifiers cannot bypass authorization;
- investigator access to evidence is correctly scoped;
- administrative operations cannot be performed by analysts.

## 11.1 IDOR tests

For every resource with an identifier:

```text

GET /api/v1/transactions/{id}
```

attempt access using:

- authorized ID;
- unauthorized ID;
- non-existent ID;
- malformed ID.

The expected result must not depend solely on whether the identifier is difficult to guess.

# 12.1 Transaction Identity, Ingestion Deduplication & Provenance Tests (TG-06)

Data ingestion tests must verify the canonical transaction identity and row-level provenance contracts established in `DATABASE_DESIGN.md` and `API_GUIDELINES.md`:

### 12.1.1 Canonical Transaction Identity
- **Natural Key Scope:** Verification that natural identity is enforced by `CONSTRAINT uq_transactions_canonical_id UNIQUE (source_namespace, account_id, external_transaction_id)`.
- **Pre-matching Account Resolution:** Test that raw import rows resolve `source_account_id` to internal canonical `accounts.id` prior to evaluating transaction identity. Missing accounts must cause row rejection, not partial transaction insertion.
- **Standalone Transactions:** Creation of standalone transactions via direct API endpoints must set `first_seen_import_id = NULL` and adhere to the same natural key constraint without requiring an associated batch import.

### 12.1.2 Repeated Import Linking & Row Provenance
- **Cross-Import Re-ingestion:** Ingesting a CSV with transactions that already exist in `transactions` under the same `(source_namespace, account_id, external_transaction_id)` must:
  - Not duplicate rows in the `transactions` table.
  - Insert row provenance entries in `transaction_import_records` with `outcome = 'MATCHED_EXISTING'` and `transaction_id` referencing the existing canonical transaction.
  - Not overwrite or alter any existing canonical attributes (`first_seen_import_id`, `occurred_at`, `amount`, etc.).
- **Intra-Import Duplicate Handling:** When the same natural key appears more than once within a single CSV payload:
  - The first valid row is inserted into `transactions` and recorded in `transaction_import_records` as `outcome = 'INSERTED'`.
  - Subsequent occurrences in the same import are recorded in `transaction_import_records` as `outcome = 'DUPLICATE_IN_IMPORT'`, with `transaction_id` linked to the canonical transaction, and must not cause primary key or unique constraint violations.

### 12.1.3 Material Conflict Quarantine
- **Conflict Detection:** When an incoming row matches `(source_namespace, account_id, external_transaction_id)` but differs materially in any of:
  - `amount` (outside exact monetary equivalence);
  - `currency` (case-insensitive string mismatch);
  - `occurred_at` (UTC timestamp divergence);
  - `account_id` (divergent resolved account);
  - `direction` (`DEBIT` vs `CREDIT`);
  - `transaction_type` (classification divergence);
  - `counterparty_account_id` (divergent counterparty);
- **Quarantine Invariant:** The pipeline must:
  - Never overwrite the existing canonical transaction row.
  - Record an error in `dataset_import_errors` with persisted `error_code = 'MATERIAL_CONFLICT'`.
  - Record an entry in `transaction_import_records` with `outcome = 'QUARANTINED'` and `transaction_id = NULL`.
  - Increment `dataset_imports.invalid_rows` and continue processing remaining rows.
  - Ensure the quarantined row remains traceable via `dataset_import_id`, `source_row_number`, and `row_hash` in `transaction_import_records`.

### 12.1.4 File-Level Deduplication, Advisory Lock & Concurrency Tests
- **Transaction-Scoped Advisory Lock Acquisition:** Verify that `POST /api/v1/datasets/imports` acquires a transaction-scoped PostgreSQL advisory lock (`pg_advisory_xact_lock`) derived deterministically from the SHA-256 `file_hash` before querying `dataset_imports`, and holds it through `dataset_imports` record creation.
- **Fast-Completion Race Condition Test:** Simulate concurrent requests A and B with identical `file_hash`:
  - Request A acquires the advisory lock, creates a `PENDING` record, processes rows, updates status to `COMPLETED`, and commits.
  - Request B, waiting on the advisory lock, unblocks upon A's commit, executes its lookup within the lock, observes status `COMPLETED`, and returns `HTTP 200 OK` with A's summary without inserting a duplicate `dataset_imports` record.
- **Concurrent Identical Upload Serialization:** Simulate two simultaneous upload requests for the same file: verify that the advisory lock serializes registration, exactly one import record is created, and the concurrent request receives `HTTP 409 Conflict` (`IMPORT_IN_PROGRESS`) without database unique constraint crashes.
- **Completed vs. Failed Precedence Test:** Seed database with a historical `FAILED` import and a subsequent `COMPLETED` import for the same `file_hash`: verify that re-uploading the file returns `HTTP 200 OK` with the completed summary. A new import attempt (`status = 'PENDING'`) is created only when **no applicable completed import exists** for that file hash.
- **Failed Import Retry Test:** When only a terminal `FAILED` import exists for `file_hash`, verify that re-uploading the file acquires the lock, creates a new `dataset_imports` attempt with status `PENDING`, and preserves the historical failed attempt intact.
- **Advisory Lock Timeout & Rollback Test:** Simulate lock acquisition contention exceeding `lock_timeout`: verify that the registration transaction immediately rolls back, no partial record is inserted, the API returns a transient error (`HTTP 503` or `408`), and the failed registration is not reported as successful.
- **Nullable File Hash Test:** Uploading an unhashed file (`file_hash = NULL`) bypasses advisory locking and file-level deduplication, allowing concurrent execution without constraint violations.
- **Different Content Re-Upload:** Uploading a distinct file (differing `file_hash`) containing overlapping transaction identities proceeds to normal row-by-row processing and records `MATCHED_EXISTING` provenance.

### 12.1.5 Row-Level Idempotent Failure Recovery
- **Crash / Resumption Verification:** If an import worker crashes mid-file, the resumption routine must not rely on `MAX(source_row_number) + 1` (which skips rows when batch inserts fail out-of-order).
- **Exact Set Reconciliation:** Resumption must query `transaction_import_records` for the specific `dataset_import_id` to determine exactly which `source_row_number` ordinals were committed, processing only uncommitted rows. Duplicate and quarantined rows remain fully auditable in `transaction_import_records` even without a canonical transaction link.

# 14. Synthetic Dataset Testing

The generator itself must be tested.

## 14.1 Reproducibility

Given:

```text
seed = 20261004
```

the generator should produce the same dataset or the same deterministic output ordering under the same configuration.

Tests should verify:

- same seed → same output;
- different seed → meaningfully different output;
- configuration changes affect output predictably.

---

## 14.2 Structural validation

Generated data should satisfy:

- expected entity relationships;
- valid foreign keys;
- unique IDs;
- valid timestamps;
- valid amounts;
- valid transaction types;
- valid account/device/location relationships.

---

## 14.3 Behavioral validation

The dataset should not merely be syntactically valid.

Tests should validate approximate behavior such as:

- different account profiles have different spending patterns;
- recurring behavior exists;
- merchant preferences are plausible;
- devices and locations have realistic reuse;
- legitimate unusual events occur;
- fraud scenarios are present.

Exact percentages should use tolerances rather than brittle equality where stochastic generation is intended.

## 14.4 Generator Identity Stability & Version Continuity Contracts (Verified in Phase 4)

The synthetic generator and ingestion test suites (`tests/unit/test_transaction_generator.py`, `tests/unit/test_generator_determinism.py`, `tests/integration/test_final_verification.py`, `tests/integration/test_advisory_lock_concurrency.py`) verify the following guarantees:

- **Identifier Stability Across Versions:** Logical transactions carried forward preserve identical `transaction_id` and `account_id` strings across identical simulated historical events.
- **Account-Scoped Determinism:** Synthetic transaction IDs (`TXN_[0-9]{8}`) remain unique per account and sequentially ordered within generator output.
- **Synthetic Namespace Isolation:** The generator defaults output namespace to `SYNTHETIC`, keeping external IDs decoupled from internal database UUIDs.
- **Seed Determinism:** Generating the dataset twice with the exact same seed and configuration yields bitwise-identical CSV outputs, ensuring reproducible evaluation benchmarks.
- **Empirical Scale Verification:** Full-scale preset verified at 250,000 transactions, 7,500 fraud transactions (3.0000% fraud rate), 3,631 scenario instances (seed 42).

# 15. Ground-Truth Isolation Tests

Fraud ground truth is available for evaluation but must never become an inference feature.

Tests must verify that:

- `is_fraud` is excluded from model feature columns;
- `fraud_scenario` is excluded;
- `scenario_instance_id` is excluded;
- investigation resolution is excluded from inference features;
- future labels cannot enter historical feature calculations.

A test should fail if any ground-truth field is accidentally added to the production feature set.

# 16. Feature Engineering Testing (Verified in Phase 6)

Feature engineering testing guarantees mathematical correctness, point-in-time temporal boundaries, schema immutability, numerical precision, and zero-leakage invariants. The Phase 6 implementation is validated across 27 automated tests organized into five dedicated suites:

### 16.1 Schema Validation & Immutability (`tests/unit/test_feature_schemas.py`)
- **34-Feature Contract Verification:** Confirms `FeatureVector` defines exactly 34 model input fields.
- **Pydantic v2 Frozen Immutability:** Asserts that mutating any field on a `FeatureVector` instance raises `pydantic.ValidationError` (error type `'frozen_instance'`).
- **Strict Attribute Rejection:** Confirms passing unexpected fields raises a validation error (`extra="forbid"`).
- **Finite Float Validation:** Asserts that non-finite floats (`NaN`, `+Inf`, `-Inf`) are rejected on any floating-point field by custom validators.
- **Metadata Decoupling:** Asserts diagnostic and operational metadata (`FeatureMetadata`) is immutable and strictly separated from the feature vector.

### 16.2 Pure Computation Engine Correctness (`tests/unit/test_feature_engine.py`)
- **Mathematical Transforms:** Hand-calculated assertions for amounts, log transforms (`math.log1p`), and dynamic point-in-time account age.
- **Negative Age Clamping:** Asserts transactions occurring prior to account DB creation clamp to `account_age_days = 0.0` and flag `is_account_created_after_txn = True` in metadata, while verifying `is_cold_start = 0` when $\ge 3$ transactions exist.
- **Sliding-Window Boundaries:** Tests inclusive lower boundaries ($t - 300\text{s}$ included in 5m velocity) and 1-second boundary exclusion ($t - 301\text{s}$ excluded from 5m velocity, included in 1h velocity).
- **Baseline Isolation:** Asserts direction- and currency-matching (DEBIT in INR is strictly isolated from CREDIT in INR and DEBIT in USD).
- **Zero-Variance Baselines:** Confirms constant historical baselines produce neutral `amount_zscore = 0.0`, `has_zero_variance_baseline = 1`, and `is_amount_different_from_constant_baseline = 1` only when the evaluated amount differs from the invariant historical mean.
- **Sparse History Sentinels:** Asserts history $< 3$ observations returns neutral sentinels (`mean_ratio = 1.0`, `median_ratio = 1.0`, `zscore = 0.0`).
- **Entity Familiarity & Missing IDs:** Confirms novelty detection, historical counts, and neutral 0 sentinels for missing device, merchant, location, and category identifiers.
- **Home Location Match:** Confirms native UUID matching against `account.home_location_id` sets `is_home_location = 1` and treats the home location as familiar (`is_new_location = 0`).
- **Location Frequency Denominator:** Asserts `location_frequency` uses total prior eligible transactions as the denominator and returns `0.0` for new accounts.
- **Category 30-Day Spend Share:** Verifies DEBIT-only matching currency over $[t - 30\text{d}, t)$, zero-denominator handling, and bounding in $[0.0, 1.0]$.
- **Temporal Boundaries:** Asserts UTC hour, day of week, weekend flags, and nocturnal unusual hour flags (`{1, 2, 3, 4, 5}` UTC).
- **Sub-Second UUID Ordering & Self-Exclusion:** Asserts deterministic tie-breaking on identical timestamps where `id < eval.id` is included and `id >= eval.id` is strictly excluded.

### 16.3 Feature Service & Streaming Batch Extraction (`tests/unit/test_feature_service.py`)
- **Non-Mutation & Ordering Preservation:** Verifies `extract_batch` does not mutate caller-owned collections, sorts an internal copy, and restores the caller's original sequence.
- **Online vs. Batch Equivalence:** Asserts batch extraction using Welford's algorithm, sliding deques, and dual heaps produces numerical agreement within $10^{-5}$ relative tolerance against pure engine evaluations on full history.
- **Multi-Account State Isolation:** Verifies interleaved batches across multiple accounts maintain completely isolated accumulators with zero cross-account state leakage.

### 16.4 PostgreSQL Repository Integration (`tests/integration/test_feature_repository.py`)
- **Bounded Window Index Scan:** Executes bounded window retrieval in PostgreSQL over `ix_transactions_account_occurred` with range pushdown.
- **Live PostgreSQL UUID Comparison:** Validates that PostgreSQL's native byte-order UUID comparison matches Python's `uuid.int` tie-breaking.
- **Lifetime Aggregations:** Verifies single-roundtrip lifetime aggregates (`COUNT`, `AVG`, `STDDEV_SAMP`, `percentile_cont(0.5)::numeric`) directly in PostgreSQL in $O(1)$ memory.
- **Error Handling:** Verifies project-standard `NotFoundError` is raised when referencing non-existent transaction or account IDs.

# 17. Temporal Leakage & Future Invariance Tests (`tests/integration/test_temporal_leakage.py`)

Temporal leakage tests are mandatory and executed against the live PostgreSQL test database:

### 17.1 Online Future-Data Invariance
Evaluates a transaction $T$, then injects 50 massive burst transactions in future time windows ($t + 5\text{m}$, $t + 1\text{d}$), and re-evaluates $T$. Asserts 100% invariance:
- Discrete/categorical features (`velocity_*_count`, `has_*`, `is_*`, temporal flags) must be bitwise identical.
- Continuous floating-point features (`amount_*`, velocities, ratios, z-scores) must match within numerical tolerance ($\le 10^{-5}$).

### 17.2 Batch Future-Data Invariance
Injects future transactions into a batch extraction dataset and asserts that earlier transactions maintain bitwise-identical feature vectors before and after future data insertion.

### 17.3 Ground-Truth Isolation
Injects synthetic transactions with active fraud labels (`is_fraud = True`, `fraud_scenario = "F001"`). Asserts that neither `is_fraud` nor `fraud_scenario` exists anywhere in `FeatureVector` or `FeatureMetadata` dictionaries or inference paths.

---

# 17.1 Feature Engineering Performance Benchmark (`tests/integration/test_feature_benchmark.py`)

A reproducible benchmark protocol validates empirical performance targets on a medium-scale dataset (100 accounts, 5,000 transactions, seed=42):

- **Batch Extraction Throughput:** Measures total wall-clock runtime for 5,000 transactions. Measured: **0.851 s** (~5,875 tx/sec), easily satisfying the $\le 3.0$ s target.
- **Peak Memory Consumption:** Measures peak memory overhead during batch extraction using `tracemalloc`. Measured: **27.82 MB**, satisfying the $\le 50.0$ MB target.
- **Single Evaluation Latency:** Measures online latency percentiles over 50 sample iterations. Measured: P50 = 7.23 ms, P90 = 8.51 ms, P95 = 8.84 ms. The P95 latency deviation against the 5.0 ms target is documented as unpooled local TCP and database connection roundtrip overhead in the test environment (the pure computation engine runs in $< 50\ \mu\text{s}$).
- **Query Plan Validation:** Inspects query execution plans via `EXPLAIN (ANALYZE, BUFFERS)`, confirming `ix_transactions_account_occurred` executes an index range scan in 0.041 ms with 3 shared buffer hits and 0 sequential scans.

# 18. ML Testing Strategy

ML testing is divided into:

1. preprocessing tests;
2. feature tests;
3. model tests;
4. scoring tests;
5. evaluation tests;
6. reproducibility tests;
7. leakage tests.

The goal is not to test scikit-learn itself. The goal is to test FinSignal's use of the ML pipeline.

### Hyperparameter Selection Discipline (Contamination)

The synthetic fraud rate (~3%) must not be blindly hard-coded as the Isolation Forest `contamination` hyperparameter without empirical justification. Tests and evaluation pipelines must verify that:
- `contamination` is evaluated as a tunable hyperparameter against validation set PR-AUC, precision, and operational alert volume.
- Anomaly prevalence is distinct from ground-truth fraud prevalence (legitimate unusual transactions may be anomalous without being fraudulent).

# 19. Model Preprocessing Tests

Verify:

- expected feature columns exist;
- column order is deterministic where required;
- missing values are handled consistently;
- categorical encoding is stable;
- numerical transformations are reproducible;
- training and inference preprocessing are equivalent;

# 20. Model Reproducibility

Tests should verify that model training is reproducible when:

- random seed is fixed;
- training dataset version is fixed;
- feature configuration is fixed;
- library/model configuration is fixed.

The model version must record enough metadata to identify the training configuration.

---

# 20.1 Model Artifact Loading & Integrity Tests (TG-02)

Tests must verify safe and resilient artifact loading:
- **Missing Artifact:** Attempting to load an artifact when the referenced file does not exist must raise a controlled `FileNotFoundError` or `ModelLoadError`, rather than crashing unhandled.
- **Corrupt / Tampered Artifact:** If the artifact file is corrupted or its SHA-256 digest fails to match `model_versions.artifact_hash`, loading must immediately abort with `ModelIntegrityError`.
- **Incompatible Feature Schema:** Loading an artifact against mismatched feature column names or counts must fail with an explicit `SchemaValidationError`.
- **Incompatible Version / Configuration:** Incompatible model serialization versions must fail with a controlled error rather than executing undefined bytecode.

---

# 20.2 Model Lifecycle Transition Tests (TG-05)

The model lifecycle follows `EXPERIMENTAL -> VALIDATED -> ACTIVE -> RETIRED`. State machine tests must verify:
- **Valid Transitions:**
  - `EXPERIMENTAL -> VALIDATED` (requires complete evaluation metrics recorded).
  - `VALIDATED -> ACTIVE` (activates model for inference; ensures only one model is active per family).
  - `ACTIVE -> RETIRED` (deactivates model cleanly).
- **Invalid Transitions:**
  - `EXPERIMENTAL -> ACTIVE` (direct promotion without validation must be rejected).
  - `RETIRED -> ACTIVE` (reactivation without a new validated release cycle must be rejected).
  - Transitions to non-existent or arbitrary statuses must be rejected.

---

# 21. Risk Scoring Tests (Phase 8 Implemented)

Risk scoring tests (`tests/unit/test_risk_scoring.py`, `tests/unit/test_risk_normalization.py`, and `tests/unit/test_risk_schemas.py`) verify:

- **Weighted Combination Correctness:** Output matches $w_{\text{ml}} \cdot S_{\text{norm}} + w_{\text{rule}} \cdot S_{\text{rule}}$ across varied input distributions.
- **Normalization Invariants:** `piecewise_linear_anchored_v1` anchors $s_{\min} \mapsto 0.0, \tau^* \mapsto 50.0, s_{\max} \mapsto 100.0$, strictly asserts $s_{\min} < \tau^* < s_{\max}$, and clamps out-of-bounds values to $[0.0, 100.0]$.
- **Risk Score Range Enforcement (TG-03):** Output is clamped to $[0.00, 100.00]$ and rounded to 2 decimal places. Pydantic schemas and PostgreSQL check constraint `chk_risk_analyses_score` enforce range bounds.
- **Tier Boundary Transitions:**
  - $0.00 \le \text{score} < 25.00 \implies \textbf{LOW}$
  - $25.00 \le \text{score} < 50.00 \implies \textbf{MEDIUM}$
  - $50.00 \le \text{score} < 75.00 \implies \textbf{HIGH}$
  - $75.00 \le \text{score} \le 100.00 \implies \textbf{CRITICAL}$
  Boundary testing at threshold $-\epsilon$, exact threshold, and threshold $+\epsilon$ confirms precise tier assignment.
- **Escalation Floors:** Optional escalation floors enforce minimum scores of $75.0$ on `CRITICAL` factors and $50.0$ on `HIGH` factors when enabled.

# 22. Risk-Factor Explainability Tests (Phase 8 Implemented)

Explainability tests (`tests/unit/test_risk_rules.py`) verify:

- **Evidence Fidelity:** Factors are generated purely from observed feature vector values and contextual comparisons; no factors are fabricated.
- **Rule Coverage:** Unit tests verify activation and point calculation across all 9 deterministic rules: `COLD_START_ACCOUNT`, `HIGH_VELOCITY`, `LARGE_AMOUNT_DEVIATION`, `NEW_DEVICE`, `NEW_LOCATION`, `UNUSUAL_TIME`, `BEHAVIORAL_SHIFT`, `NEW_MERCHANT`, `NEW_CATEGORY`.
- **Severity & Points Scaling:** Velocity and amount deviation scale from `MEDIUM` (15 pts) through `HIGH` (25 pts) to `CRITICAL` (40 pts) as thresholds increase.
- **Suppression Logic:** `COLD_START_ACCOUNT` suppresses false amount-deviation spikes on unestablished accounts; `NEW_CATEGORY` is suppressed when `BEHAVIORAL_SHIFT` is active to avoid redundant penalties.
- **Bounded Rule Sum:** Total rule score is bounded: $S_{\text{rule}} = \min(100.0, \sum \text{points})$.
- **Payload Schema Validation:** Every factor populates `factor_code`, `factor_label`, `severity`, `description`, and structured `evidence` dictionary matching API and DB contracts.

   - Tests atomic rollback: an intentional failure during audit event insertion rolls back the investigation and primary link, preventing partial persistence.
   - Tests partial unique index `uq_investigation_single_primary`: attempting to insert a second `PRIMARY` transaction raises PostgreSQL unique violation `23505`.
   - Tests CHECK constraint `chk_investigations_resolution_state`: rejects `RESOLVED` cases with missing or whitespace-only resolution notes.
   - Tests PostgreSQL trigger `trg_no_update_delete_evidence`: direct SQL `UPDATE` and `DELETE` on `investigation_evidence` are intercepted and rejected with an exception.

5. **Multi-Connection Concurrency Integration Tests (`tests/integration/test_investigation_concurrency.py` — 3 tests):**
   - Concurrent self-assignment race across two independent PostgreSQL connections: row lock (`SELECT ... FOR UPDATE`) ensures exactly one investigator claims the case (200 OK) while the racing investigator receives 409 `CASE_ALREADY_ASSIGNED`.
   - Explicit peer takeover prevention: Investigator 2 attempting to claim Investigator 1's assigned case receives 403 `FORBIDDEN`.
   - Concurrent resolution race across two independent PostgreSQL connections: one caller succeeds, second caller receives 409 `INVESTIGATION_ALREADY_RESOLVED`.

# 45. Test Data Isolation

Test data must never be confused with production data.

Requirements:

- separate database/schema;
- synthetic test data;

- isolated storage;
- test-specific secrets.

Production credentials must never be loaded by automated tests.

# 46. Failure Injection and Resilience

Important failure modes should be tested deliberately.

Examples:

- PostgreSQL unavailable;
- database connection failure;
- LLM timeout;
- malformed model artifact;
- missing model version;
- invalid dataset;
- insufficient disk space;
- interrupted import;
- duplicate import;
- transaction rollback.

Expected behavior should be:

- controlled;
- observable;
- non-corrupting;
- recoverable where possible.

The system must not report successful processing when a critical downstream operation failed.

---

# 47. Transaction Rollback Tests

When a multi-step operation fails, database state must remain consistent.

Example:

```text
Create dataset import
→ insert valid records
→ encounter fatal error
→ rollback
```

The test should verify that partially persisted state is either rolled back or explicitly represented as a failed/partial import according to the documented design.

No silent partial success.

- login;

- investigation resolution;

Tests should also verify that logs do not contain:

# 49. Coverage Strategy

Coverage is a signal, not the objective.

High coverage should be expected for:

- domain logic;
- financial calculations;
- authorization;
- feature engineering;
- risk scoring;
- investigation state transitions;
- validation;
- security-sensitive code.

Lower coverage may be acceptable for:

- trivial configuration;
- framework wiring;
- generated code;
- thin adapters.

Coverage should be reviewed alongside test quality.

A high percentage achieved through weak assertions is not considered success.

---

# 50. Mutation / Adversarial Testing

Where practical, important logic should be tested against deliberately incorrect inputs.

Examples:

- flip transaction direction;
- alter timestamp;
- remove a required risk factor;
- inject future transaction;
- modify account ID;
- alter risk threshold;
- replace evidence with unrelated evidence.

The goal is to verify that tests detect meaningful correctness violations.

Mutation testing may be introduced selectively after the core suite is stable.

---

# 51. Flaky Test Policy

Flaky tests must not be normalized.

When a test is flaky:

1. identify the source;
2. reproduce it;
3. fix the underlying nondeterminism;
4. avoid simply increasing retry counts.

Common causes to avoid:

- wall-clock dependence;
- random seeds;
- unordered database results;
- shared mutable fixtures;
- external service dependency;
- asynchronous race conditions.

If ordering matters, make ordering explicit.

---

# 52. Test Ordering and Isolation

Tests should pass independently.

Do not rely on:

```text
test_A runs before test_B
```

Each test should establish its required state.

Database tests should use transaction rollback or isolated fixtures where appropriate.

Shared state should be read-only or reset between tests.

A pull request should not merge when:

- security tests fail;
- type checking fails where required;
- linting/formatting fails;
- critical coverage regresses without justification;
- temporal leakage tests fail;
- ground-truth isolation tests fail.

ML changes should additionally include evaluation evidence when model behavior changes materially.

# 55. ML Change Validation

A change to:

- features;
- preprocessing;
- model;
- scoring;
- thresholds;
- scenario logic;

must trigger appropriate regression evaluation.

At minimum compare:

- precision;
- recall;
- F1;
- PR-AUC;
- alert volume;
- false-positive behavior;
- scenario-level detection.

A model should not be accepted solely because one aggregate metric improved.

# 56. Regression Test Suite

A stable regression suite should preserve previously discovered failure cases.

Every significant production-like bug should result in:

- duplicate transaction import;
- incorrect transfer handling;
- wrong risk threshold;
- hallucinated AI evidence.

# 65. Final Testing Principle

FinSignal should not be considered correct merely because:

- the API returns `200`;
- the model produces a score;
- the dashboard renders;
- the dataset loads;
- the test coverage percentage is high.

The system is correct only when its outputs are:

**financially accurate, temporally correct, reproducible, secure, explainable, evidence-grounded, and appropriately subject to human review.**

The most important tests are therefore the ones that prevent the system from confidently producing the wrong conclusion.
